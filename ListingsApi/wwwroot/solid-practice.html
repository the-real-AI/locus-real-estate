Архитектурный фундамент

Что означает аббревиатура SOLID

Сформулированы Робертом Мартином для борьбы с тремя болезнями кода: жесткостью, хрупкостью и неподвижностью.

S

Single Responsibility

Единственная ответственность

У класса должна быть только одна причина для изменения. Класс отвечает за одну конкретную задачу.

Симптом: Класс одновременно валидирует, пишет в базу, формирует отчет и шлет письма.
O

Open / Closed

Открытость / Закрытость

Сущности открыты для расширения, но закрыты для изменения. Новое поведение — это новый класс, а не ветка switch.

Симптом: Для нового тарифа или типа квартиры дописывается очередная ветка if / switch.
L

Liskov Substitution

Подстановка Лисков

Наследник должен заменять базовый класс, не ломая программу. Клиент базового типа не должен замечать подмены.

Симптом: Метод наследника бросает NotSupportedException или требует проверку is Subclass.
I

Interface Segregation

Разделение интерфейсов

Клиент не должен зависеть от методов, которыми не пользуется. Много узких интерфейсов лучше одного жирного.

Симптом: Интерфейс INotifier требует реализовать Push-уведомления там, где они не поддерживаются.
D

Dependency Inversion

Инверсия зависимостей

Модули верхнего уровня зависят от абстракций, а не от деталей. Зависимости передаются снаружи через конструктор (DI).

Симптом: Сервис прямо в коде пишет new SqliteConnection() или new SmtpClient().

checklist Чек-лист самопроверки SOLID

S
Вопрос: Могу ли я назвать класс двумя словами через «и» (например, «хранит и печатает»)? Если ДА — принцип нарушен!
O
Вопрос: Чтобы добавить новый вариант, я открываю старый файл и дописываю ветку if/switch? Если ДА — принцип нарушен!
L
Вопрос: Есть ли в наследнике override, который бросает NotSupportedException или игнорирует параметр? Если ДА — LSP нарушен!
I
Вопрос: Есть ли реализация интерфейса с методом-заглушкой (пустое тело / throw)? Если ДА — разделите интерфейс!
D
Вопрос: Есть ли в классе с бизнес-логикой слово new для базы, файла, почты, сети? Если ДА — внедрите зависимость!
